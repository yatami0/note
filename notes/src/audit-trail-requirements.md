# 業務システムのユーザー単位監査証跡

「どの個人が・いつ・何をしたか」をシステム側の記録として追跡できること。認証アーキテクチャの選択（[[oauth-client-credentials]]か[[oidc-federation]]か）を最終的に決めるのは、技術の優劣ではなくこの要件の有無。

## なぜアプリ名義の認証では監査的にまずくなりうるか

外部アプリが[[oauth-client-credentials|client_credentials]]でAPIを呼ぶ構成では:

1. **トレーサビリティの喪失**: APIログの操作主体が全て「そのアプリ」に潰れる。「誰が・いつ・どのデータを参照/変更したか」に自分のログ単独では答えられない。記録されていないものは後から復元できない
2. **職務分掌（SoD）の検証不能**: 「承認者と起票者が別人か」のような統制はユーザー識別が前提
3. **相手ログとの突合依存**: 「相手側のログと突き合わせればよい」は一応の反論だが、ログの完全性・改ざん耐性・保持期間・時刻同期を**他社に依存**することになり、監査境界が広がって説明コストが増える
4. **「ユーザーIDヘッダを付けてもらう」は解決にならない**: 自己申告は認証ではない。IdPが署名したクレームとして`sub`に載る場合と証拠能力が根本的に違う

## 要件の出どころ（IETFには答えがない）

OAuth/IETFの標準は「どう作るか」の標準であって「何を残すべきか」の基準ではない。監査要件の出どころは法令・基準・監査人:

| 出どころ | 具体的に見るもの | 関係 |
|---|---|---|
| **J-SOX（金商法・内部統制報告制度）** | 金融庁「財務報告に係る内部統制の評価及び監査に関する実施基準」— IT統制（ITGC）の「アクセス管理」 | 会計データを扱う基幹システムはど真ん中の対象。上場企業（連結子会社含む）なら毎年ITGC評価が入る |
| 経済産業省 | 「システム管理基準」「システム監査基準」 | 国内システム監査の一般基準 |
| ISACA | **COBIT** | ITGCの国際フレームワーク。監査法人のIT監査はほぼこれ系の観点 |
| ISO/IEC | **27001/27002**（ISMS）のログ取得・アクセス制御の管理策 | ISMS認証を持つ会社なら内部監査でも見られる |
| NIST | SP 800-53のAU（監査）・AC（アクセス制御）ファミリ | 要件の粒度感の参考 |
| 業界固有 | 金融ならFISC安全対策基準、医療なら3省2ガイドライン | 業種による上乗せ |

**実務上の最短経路**は文書を読むことではなく、**要件の決定者に聞くこと**: システムがJ-SOXの評価範囲に入るかを確認→入るなら内部監査部門・経理部門・監査法人のIT監査担当に「ユーザー単位の操作証跡は必要か」を確認（会計系ならほぼ確実にYes）。**文書で回答をもらう**ことに意味がある（方式変更・追加費用の根拠になる）。

要件が決まっていないのに方式を先に決めるのは順序が逆。「我々はこの方式がやりたい」ではなく「**要件がこの方式を要求するかを確定してくれ**」という形でエスカレーションし、判断責任を要件のオーナーに置く。

## 監査ログに何を残すか（ドラフト仕様）

| フィールド | 内容 | 取得元 |
|---|---|---|
| `who` | 操作者 | JWT `sub`（+`email`等のクレーム） |
| `via` | 経由アプリ | JWT `azp` / `client_id` |
| `when` | 時刻（UTC, ISO8601） | サーバ時刻（NTP同期前提） |
| `what` | 操作内容 | エンドポイント＋メソッド＋対象リソースID |
| `result` | 成功/失敗 | レスポンス（4xx/5xx区分） |
| `request_id` | 追跡ID | ミドルウェアで採番、サービス間で伝搬 |

トークン自体はログに出さない（`Authorization`ヘッダをアクセスログから除外）。更新系は変更前後の値を残すかを業務側と確認。長期保管・改ざん防止（S3アーカイブ等）は保存期間要件と合わせて設計。
