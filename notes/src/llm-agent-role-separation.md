# 対話LLMとリポジトリ操作エージェントの分離

チャットUIからLLMと壁打ちし、その結果をリポジトリのコンテンツとして保存する仕組みを作るとき、**1つのチャットセッションに最後までやらせたくなる**。が、対話とリポジトリ操作は要求されるものが違うので、2つの役に分けたほうが素直に組める。

## 何が違うのか

| | 対話用LLM | リポジトリ操作エージェント |
|---|---|---|
| 起動場所 | ブラウザ ↔ エッジのプロキシ | CI（リポジトリをチェックアウト済み） |
| 求められるもの | 低レイテンシ・ストリーミング | 正確さ・規約遵守。数分かかってよい |
| 文脈 | 選択テキスト + 当該ドキュメント + 隣接数件 | リポジトリ全体 |
| 権限 | 読み取りのみ | ファイル作成・書き換え・ブランチ push |
| 失敗の直し方 | ユーザーがその場で聞き直す | CI（テスト・ビルド）で検出してPRで止める |

分けないと何が起きるかというと、チャット側にファイルを書かせることになり、**リポジトリ固有の規約をどれも守れない**。このノートリポジトリで言えば、1ノート1概念の粒度、既存ノートをgrepしてリンクを張る、タグの表記、ファイル名のkebab-case、frontmatterの自動付与——どれもリポジトリ全体を見ないと判断できない。

## 引き継ぎの成果物

分けた以上、対話からエージェントへ渡すものを決める必要がある。最小限は次の3つ。

- **会話ログ** — 何を疑問に思い、どう納得したか。ノートの素材そのもの
- **選択アンカー** — どのドキュメントのどこから始まった対話か（ドキュメントID + 選択テキスト、できれば元ソース上の位置）
- **ユーザーの意図** — 新規作成か既存への追記か

会話ログは**成果物には混ぜない**。壁打ちの過程をそのままノートにすると、1ノート1概念が壊れる。ログはPR本文や起動用Issueに置いて、成果物は書き直したものにする。

## 文脈が全部入るなら検索はいらない

「エージェント側にリポジトリ全体を渡す」は、規模次第では素直に実現できる。このリポジトリは42ノート・約191KBで、日本語主体なので概ね6〜7万トークン。100万トークンのコンテキストに対して**全文がそのまま入る**。

つまりベクトルDBもチャンク分割も要らない。関連ノートを「検索して見つける」のではなく、**全部見せて選ばせる**ほうが精度も実装の単純さも上。プロンプトキャッシュを効かせれば、2回目以降の入力コストは1桁下がる。

RAGを組む前に「そもそも全部入らないか」を測るのは、この規模の個人プロジェクトでは毎回やる価値がある。対話側は逆に、全文を毎ターン送る必要はない（レイテンシとコストが効くので、選択箇所とその周辺だけでよい）。ここでも2つの役の性質の違いが出る。

## 起動口の設計が権限設計になる

エージェント側は書き込み権限を持つので、**誰が起動できるか**が実質的な権限境界になる。CIをIssueやコメントで起動する設計にすると、Issueを立てられる人＝エージェントを動かせる人になる。公開リポジトリならそれは全世界を意味する（[[repo-visibility-and-automation]]）。

対話側に必要なのは読み取りだけなので、権限を持つのはエージェント側に閉じ込め、対話側からは「起動を依頼する」だけにできるとよい。

## このサイトでの適用
