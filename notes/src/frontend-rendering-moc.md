# フロントエンドのレンダリング境界の見取り図（MOC）

「サーバとクライアントの境界をどこに引くか」に関する原子ノートの見取り図。発端は「ずっとReactを使ってきたが、今回このノートサイトを[[astro|Astro]]で作っている。何が違うのか」という問い。

この領域の話は用語（SSR / SSG / CSR / RSC / islands / streaming）が乱立して見えるが、問いは1つしかない。**どのコードをサーバで実行し、どのコードをブラウザに配るのか**。各技術はその線の引き方と、引く手段（言語・型・宣言）が違うだけ。

## なぜ境界が問題になるのか

- [[hydration]] — 全ての出発点。サーバが返せるのは文字列だけなので、イベントハンドラを結び直すためにクライアントで**同じツリーを再実行**する必要がある。この二重実行のコストが「見えているのに押せない」区間を生む。以降のノートはすべて、このコストの削り方の変種

## 境界の引き方（3つの系統）

同じ目的（クライアントJSを減らす）に対し、切る**レイヤ**が違う。

- [[islands-architecture]] — **フレームワークの外側**で切る。静的HTMLの海に独立した島を置く。島の中身はReactでもVueでもよいが、島同士は状態を共有できない
- [[react-server-components]] — **Reactの型（コンポーネント種別）**で切る。ツリー全体がReactのまま、`'use client'`が境界。サーバ→クライアントを跨いだ1つのツリーとして設計できる
- [[astro]] — **言語**で切る。`.astro`はサーバでしか動かないファイル形式で、境界がファイル単位で目に見える。島の仕組みを最初に前面に出したフレームワーク

## 土台にある思想

- [[progressive-enhancement]] — 2003年からある考え方だが、上の3系統はどれもこの再発見と読める。最小構成（HTML）を土台に、必要な段階まで上げてそこで止める。「JSを使うな」ではなく**どこで止めるかの物差し**

## 選び分けの早見

| 作るもの | 向く構成 |
|---|---|
| ブログ・ドキュメント・LP（読み物が主） | Astro（島ゼロ〜数個） |
| 記事＋検索/コメントのような局所的な動き | アイランド |
| 認証付きでデータ量が多い業務アプリ、パーソナライズが深い | RSC（Next.js等） |
| エディタ・ダッシュボード・チャット（画面全体が1つの状態機械） | 素直にSPA |

判断に迷ったら「**このページをリロードしたら壊れる状態がどれだけあるか**」を数える。ゼロに近いほど左（サーバ寄り）でよい。

## 隣接する話題

- [[nextjs-token-exposure]] — 境界を跨ぐデータは直列化されてブラウザに届く、という性質が事故になる側面。認証認可側からの視点は[[web-auth-moc]]
- [[cloudflare-workers]] — 生成した静的アセットとサーバサイド実行の置き場。このノートサイト自身の配信先
