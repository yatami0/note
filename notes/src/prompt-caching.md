# プロンプトキャッシュ

LLM APIで、プロンプトの前方部分（プレフィックス）の推論結果をサーバ側に保持し、次のリクエストで再利用する仕組み。同じ長い文脈を何度も送る使い方——エージェント、長い会話、大きな資料を前提にしたQ&A——でコストとレイテンシが大きく下がる。

## 唯一の不変条件

**プレフィックス一致である。プレフィックスのどこか1バイトでも変われば、それ以降のキャッシュは全部無効になる。**

キャッシュキーは、レンダリングされたプロンプトのバイト列から作られる。位置Nに1文字の差があれば、N以降のキャッシュはすべて外れる。

レンダリング順は `tools` → `system` → `messages`。だから**マーカーをどこに置くかより、プロンプトを組み立てる順序のほうが効く**。安定したものを前に、揮発するものを後ろに並べる。この順序が正しければキャッシュはほぼ勝手に効くし、逆なら`cache_control`をいくつ置いても効かない。

分類の目安:

| 変化の頻度 | 置く場所 |
|---|---|
| 決して変わらない | 最前（ツール定義・不変のシステムプロンプト） |
| セッション単位で変わる | 共通プレフィックスの後ろ |
| ターン単位で変わる | 末尾（最後のブレークポイントより後） |
| リクエスト毎に変わる（時刻・UUID） | 消すか、最後尾へ動かす |

## 黙ってキャッシュを壊すもの

エラーにならず、ただヒット率がゼロになるので気づきにくい。

| パターン | なぜ壊れるか |
|---|---|
| システムプロンプトに`Date.now()`や現在時刻を埋める | 毎リクエストでプレフィックスが変わる |
| UUID・リクエストIDを前方に入れる | 同上 |
| `JSON.stringify`でキー順が非決定的、`Set`をそのまま出力 | バイト列が揺れる |
| システムプロンプトを条件分岐で組み立てる | フラグの組み合わせごとに別プレフィックスになる |
| ユーザーごとにツールセットを変える | ツールは位置0に描画されるので全部無効 |
| 会話の途中でモデルを切り替える | キャッシュはモデル単位 |

「現在日時を渡したい」「モードを切り替えたい」は、システムプロンプトを書き換えるのではなく**会話の末尾に足す**のが正解。5ターン目に足したものは、4ターン目までのキャッシュを壊さない。

## 無効化には階層がある

すべての変更が全部を壊すわけではない。`tools` / `system` / `messages` の3層があり、変更は自分の層から下だけを無効化する。

- ツール定義の変更・モデル切り替え → 全部無効
- システムプロンプトの変更 → toolsは生存、system以降が無効
- メッセージ内容の変更 → tools + systemは生存

つまり`tool_choice`の切り替えや思考モードのon/offは、tools+systemのキャッシュを保ったままできる。本当に警戒すべきはツール定義とモデルの変更だけ。

## 損得の計算

- **読み**: 通常の入力価格の約0.1倍
- **書き**: 5分TTLで1.25倍、1時間TTLで2倍

5分TTLなら**2回目のリクエストで元が取れる**（1.25 + 0.1 = 1.35 < 2）。1時間TTLは3回必要（2 + 0.2 = 2.2 < 3）。長いTTLはトラフィックに間隔が空くケースを救うが、書き込みが倍になるぶん元を取るのに回数が要る。

**最小キャッシュ長がモデルごとに違い、しかも新しいほど小さいとは限らない**点は罠。2026年8月時点で Claude Opus 5 / Fable 5 は512トークン、Opus 4.8 / Sonnet 5 は1024、Opus 4.6 / Haiku 4.5 は4096。これを下回るとマーカーを置いてもエラーにならず、静かにキャッシュされない。

## 効いているかの確認

レスポンスの`usage`を見る。

- `cache_read_input_tokens` — キャッシュから読んだ量（0.1倍で課金）
- `cache_creation_input_tokens` — 書いた量（1.25倍）
- `input_tokens` — **未キャッシュの残りだけ**

3つ目を勘違いしやすい。プロンプト全体のサイズは3つの合計で、`input_tokens`が小さいのは「入力が少ない」のではなく「大半がキャッシュから来た」の意味。同じプレフィックスで繰り返しているのに`cache_read_input_tokens`が常に0なら、上の表のどれかを踏んでいる。

## 細かい挙動

- 1リクエストあたりのブレークポイントは最大4つ。
- 各ブレークポイントは**直前20ブロックまで**しか遡って過去のキャッシュを探さない。1ターンで20を超えるブロック（ツール呼び出しが連続するエージェントで起きる）が積まれると、次のリクエストが過去のキャッシュを見つけられず静かに外れる。
- 並行リクエストは互いのキャッシュを読めない。キャッシュが読めるようになるのは**最初のレスポンスがストリームを開始してから**。同じプレフィックスでN本同時に投げると全部が満額になる。1本投げて最初のトークンが返ってから残りを流す。

## このサイトでの使いどころ

[[llm-agent-role-separation|ノート化エージェント]]にはノート全文（6〜7万トークン）を毎回渡す設計にしている。ここが典型的な「大きくて安定したプレフィックス」で、キャッシュが最も効く形。逆に対話側は毎回文脈が違うので、キャッシュ前提の設計にはしない。
