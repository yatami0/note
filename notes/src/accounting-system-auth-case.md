# 社内基幹システムの認証方式選定（ケース記録）

[[browser-token-tradeoff]]の判断フレームワークを実際の案件に適用した記録。概念の説明は各リンク先に切り出し、ここには前提・判断・スタンスだけを残す。

## 前提

- 提供するもの: **マスタデータ管理サービス**＋**会計トランザクション管理サービス**（それぞれDB＋参照/更新サイト）。現行はSalesforceで運用中、AWSへ移行
- 別ベンダーがコアシステム（Webアプリ）を開発し、我々のAPIからデータを取得する（同一Kubernetesクラスタ内）
- 利用者: 社内ユーザー（我々のサイトもベンダーアプリも使う）＋外部ユーザー（ベンダーアプリからアカウント払い出し）
- 関係者間で「認証基盤を統一したい」という議論が発生

## 確定した技術方針

| # | 確定事項 | 根拠 |
|---|---|---|
| 1 | Web UIは[[bff-pattern|BFFパターン]]（トークンをブラウザのJSに一切露出しない） | [[oauth-browser-based-apps|IETFドラフト]]が業務・機微データに強く推奨。[[xss-token-theft|XSS時の爆発半径]]が構造的に小さい |
| 2 | セッションは第一案Redis（1a）、代替案[[stateless-session|暗号化Cookie＋IdPリフレッシュ（1b′）]]の2案並行提示。**分岐条件は[[token-revocation|失効遅延の許容値]]**（0秒必須→1a、AT寿命5〜15分の遅延許容→1b′可）。セッション層はインターフェースで抽象化し両対応で実装 | 監査要件の回答待ちで実装を止めないため |
| 3 | APIは共通IdP発行のJWTのみ受け付ける[[oauth-resource-server|OAuthリソースサーバ]]として作る | 呼び出し元（BFF/ベンダー）で分岐しない。方式論争と切り離して着手できる |
| 4 | バッチ・システム間連携は[[oauth-client-credentials|client_credentials]] | 人間が介在しない通信の標準形 |
| 5 | 同一クラスタ/Podでも認証は省略しない | ゼロトラスト。別ベンダーのコードが同居するならなおさら |
| 6 | Next.jsの[[nextjs-token-exposure|トークン非露出5ルール]]＋CSP＋[[csrf|CSRF]]対策を実装規律として固定 | BFFは「自動で安全」ではないため |

判断の決め手（[[browser-token-tradeoff]]の質問リスト適用）: 資産価値=高（会計・基幹マスタ）、即時失効=事実上の要件（退職者・異動者の無効化、内部統制）、マルチクライアント要件はAPI層のみ実在、Redis運用コスト=ElastiCacheで軽微 → **BFF+セッションが正当化される典型ケース**だった。

## 論点①: 個人単位の操作証跡は要件か（未確定・エスカレーション中）

ベンダーアプリ経由の操作が[[oauth-client-credentials|client_credentials]]のままだと、APIログの操作主体が全て「vendor-app」名義に潰れる（[[audit-trail-requirements]]）。会計データを扱う以上J-SOXのITGC評価範囲に入る可能性が高く、その場合ユーザー単位の証跡が必要 → [[oidc-federation|フェデレーション（方式b）]]が必須になる。

スタンスは3層に分けて持つ:

1. **技術（不変・今すぐ着手）**: APIはリソースサーバとして作る。(a)/(b)の差は`sub`の扱い程度で、API実装は方式決定を待たずに進む
2. **要件（エスカレーション）**: 「ユーザー単位の証跡がどこまで必要か」は我々が決められる事項ではない。「我々は(b)がやりたい」ではなく「**要件が(b)を要求するかを確定してくれ**」という形で発注元に文書回答を求める（判断責任を要件のオーナーに置く）
3. **契約（変更管理）**: 当初想定は(a)相当。証跡要件が確定するなら(b)へのスコープ変更であり、責務分担表と費用/工期影響を添えて変更管理プロセスで合意する。追加が発生するのは我々だけではない（ベンダーのOIDC改修の方がむしろ大きい）

方式(b)でも「認証を全部背負う」わけではない: 社内ユーザーの本人確認は既存ID基盤（実体はGoogle Workspace）への[[oidc-federation|フェデレーション]]で情シス側に残り、外部ユーザーの払い出し・棚卸しはベンダーに委譲可能（ガバナンスは持つ、運用実務は持たない、を分担表で明文化）。

## 「認証基盤を統一したい」へのスタンス（ケース別）

不変の原則: **APIが信頼するトークン発行元（iss）は1つ。クレーム仕様（aud/scope/sub）は我々が定義する。IdPの実体がどこの誰でも、この契約面は我々が握る。**

| ケース | スタンス |
|---|---|
| 全社主導で統一IdPが建つ | 乗る。トークン仕様書・スコープ表を先に提示し「統一IdPが満たすべき仕様」を定義する側に回る |
| 我々がIdPオーナーを振られる | ガバナンスは持ち運用実務は持たない、を分担表で明文化して条件付きで受ける |
| 統一が進まない＋証跡要件Yes | 我々のCognitoをベンダーに開放する「ミニ統一」。issを設定値化し将来の全社IdPに挿し替え可能にしておく |
| 統一が進まない＋証跡要件No | 方式(a)維持＋リスク受容の文書化。APIは`sub`対応済みにして将来の移行コストを最小化 |
| ベンダーIdPへの統一に転ぶ | 技術的には成立（issの差し替え）。ただし会計データのアクセス統制の鍵を他社運用に委ねる統制リスクを提示し、仕様・SLA・ログ提供義務を契約化 |

全ケース共通の先手: ①トークン仕様書、②スコープ表、③クライアント登録手順、④責務分担表——「API利用の約款」4点セットをどのケースでも使い回せる形で先に作っておく。

## 進め方（フェーズ分割の骨子)

- **フェーズ1（要件回答を待たずに先行）**: IdP最小構成＋API のJWT検証・scope認可・監査ログ＋BFFセッション基盤（1a/1b′両対応）＋Next.js非露出規律。**この範囲は論点①がどちらに転んでも変わらない**
- **ゲート**: 論点①の文書回答受領
- **フェーズ2A/2B**: (a)接続 or (b)展開（AD/Google連携・外部ユーザー収容・ベンダーOIDC改修）
- **フェーズ3**: 結合・失効シナリオ試験・監査リハーサル（「この操作をしたのは誰か」をログから実演）・Runbook
