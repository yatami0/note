# トークンをブラウザに出すかの判断基準

「BFF+セッション vs SPA+ブラウザ保持トークン」の議論の中心となる問いはこれ:

> **トークンをブラウザに出す代わりに得るものが、そのXSSリスクとBFFコストに見合うか？**

抽象的な「メリット」で終わらせず、得るものが実在するかを1つずつ潰して判断する。

## 「得るもの」の3分解と実在チェック

| 得るもの | 本当に価値がある条件 | 落とし穴 |
|---|---|---|
| (1) サーバのステートレス性 | 超大規模・水平スケール要件・ストア運用が真に重荷 | JWT自体はBFFでもサーバ保持できる（[[session-id-vs-jwt]]）。失うのは「ストアを持つコスト」だけで、代わりに[[token-revocation|即時失効]]を失う。社内システム規模なら同時セッションは数百〜数千のオーダーでストア運用は軽い |
| (2) 実装の単純さ | 素のAPI構成でBFF層追加が重い | 「安全なSPAトークン方式」（メモリ保持＋HttpOnlyリフレッシュ＋サイレントリフレッシュ＋ローテーション＋失効検知）は結局複雑。Next.js App RouterならRoute Handler/Server Actionが**既にBFF**で、優位はむしろ逆転する |
| (3) マルチクライアント | Web以外のクライアントが**現に**存在・確定 | 「将来モバイルを出すかも」はYAGNI。また要件が実在しても、それは**API層をリソースサーバにする話**であってブラウザにトークンを出す理由にならない（[[oauth-resource-server]]） |

## ブラウザ保持が実際に正当化されるケース

いずれも「**BFFが物理的・組織的に置けない**」が本質:

1. **バックエンドを一切持てない**: 純粋な静的ホスティングのみ（S3+CloudFrontだけ等）で完結させたい小物ツール。BFFを置く場所自体がない
2. **第三者のAPIをブラウザから直接叩く必要がある**: 例えばMicrosoft GraphをMSAL.jsで直接呼ぶ構成。全トラフィックを自前BFFでプロキシするとレイテンシ・転送コスト・レート制限の付け替えが発生し、他社APIの単なる土管になる
3. **BFFプロキシが性能上のボトルネック**: ブラウザ→リソースサーバの通信量が膨大（大容量メディア、リアルタイム系）→ これは[[oauth-browser-based-apps|TMB（パターン2）]]の出番
4. **組織的制約**: フロントとAPIが完全に別組織・別ドメインで、同一オリジンのバックエンドを誰も持てない

**性能・スケーラビリティを理由にパターン3（素のSPA+トークン）を選ぶ正当化はIETFドラフト上存在しない**。

## BFF側のコスト（天秤の反対側）

- セッションストアの導入・運用（ストアの可用性＝認証の可用性になる。マネージドなら軽い）
- ステートフル化（スティッキーではなく共有ストア前提にすれば済む）
- [[csrf|CSRF]]対策（`SameSite`+Origin検証で負担は小さい）
- デバッグ・テストの複雑さ（トークン方式でもリフレッシュ処理のテストは必要で、差は小さい）

## 意思決定基準（決定的な質問リスト）

1. このサービスで扱う資産の価値は？（漏洩被害の大きさ）
2. 攻撃面はどれくらい広い？（サードパーティスクリプト・依存の多さ。[[xss-token-theft]]）
3. 即時失効・集中管理は要件か？（コンプラ、退職者無効化。[[audit-trail-requirements]]）
4. 実在するマルチクライアント要件はあるか？（今、確定しているか）
5. ストア運用のコストは現実的に重いか？
6. トークン非露出の規律を維持できるか？（[[nextjs-token-exposure]]）

→ 1〜3が「重い/要る」に寄り、4〜5が「軽い/不要」に寄るほど**BFF+セッション**が正当化される。逆に4が強く実在し1〜3が軽いなら**トークン方式**が正当化される。

会計データ・基幹マスタを扱う社内システムに当てはめた実例は[[accounting-system-auth-case]]。
