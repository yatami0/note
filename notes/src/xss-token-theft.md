# XSSとトークン窃取の爆発半径

認証方式選定で「XSSリスクを引き受ける」と言うとき、その確率と影響を具体化しないと天秤が組めない。セキュリティ設計の観点では「侵害の発生」ではなく「**侵害の爆発半径**」を比べるべき。

## 発生確率: 「自分のコードは大丈夫」では見積もれない

- XSSはOWASP Top 10で恒常的に上位。「よく分かっているチームでも混入する」クラスの脆弱性
- React/Next.jsはデフォルトでエスケープするため素のXSSは起きにくいが、`dangerouslySetInnerHTML`、`href`へのユーザー入力（`javascript:`）、markdownレンダラ、リッチテキストエディタ等が典型的な穴
- **自前コードよりも依存とサードパーティスクリプトが主戦場**。2024年のpolyfill.io事件のように、読み込んでいる外部スクリプトのサプライチェーン侵害は自分の実装品質と無関係に発生する
- 社内システムなら広告・解析タグ等がほぼゼロで攻撃面は狭いが、npm依存のサプライチェーンリスクは残る

## XSS発生時に起きることの比較（ここが本質的な差）

| | SPA + ブラウザ保持トークン | [[bff-pattern|BFF]] + HttpOnlyセッション |
|---|---|---|
| 攻撃者ができること | トークンを**持ち出し**、攻撃者のサーバから直接APIを叩ける | Cookieは読めない。被害者のブラウザ内から**セッションに相乗り**（session riding）してAPIを叩けるのみ |
| 被害の持続時間 | **トークン有効期限まで**（RTも取られれば事実上無期限） | **被害者がタブを開いている間だけ** |
| 失効 | 不可能（JWTは期限まで有効。[[token-revocation]]） | **サーバ側セッション削除で即時全滅** |
| 被害の場所 | 攻撃者のインフラ（オフライン・並列・自動化し放題） | 被害者のブラウザ内（挙動が監視・検知されうる） |
| 発覚後の対応 | 鍵ローテーション＋全ユーザー再ログインなど大掛かり | 該当セッション削除、全セッション削除も一撃 |

「XSSがあればBFFでもAPIは叩ける」という反論は事実だが、**持続時間・実行場所・失効可否がすべて違う**。BFFは半径が構造的に小さい。

もう1つの非対称性: BFF方式は「トークン非露出」を実装規律で担保できる余地がある（[[nextjs-token-exposure]]）が、SPA方式は「トークンがJSから読める」ことが**設計上の前提**なので、規律でリスクをゼロに近づける余地自体がない。

## CSPの位置づけ

- nonce/hashベースの厳格な`script-src`（strict-dynamic）はXSSの実害（外部への持ち出し、任意スクリプト実行）を大きく削れる
- ただしCSPは**緩和策であって保証ではない**: 設定ミス（`unsafe-inline`残存）、許可済みドメイン上のJSONP/ガジェット経由のバイパス、`connect-src`を絞らないと持ち出しは防げない、等
- CSPがあるとSPA方式の期待被害は下がるが、「XSS前提でも被害が封じ込められる」というBFFの構造的優位は消えない。**CSPはどちらの方式でも入れるべきもの**であり、方式選択の代替にはならない

## 脅威モデルの明示

天秤を組む前に書き出すもの:

- 守る資産の価値（金融/医療/管理者権限か、影響の小さい社内ツールか）
- 攻撃者の想定（無差別botか、フィッシング経由の端末侵害・退職者の残存アクセスのような標的型か）
- 侵害時の最悪シナリオ（何が起きると事業として致命的か）

「XSSが絶対にない」は証明不能な前提（不在の証明はできない／存在は1例で証明される）。堅牢な設計とは壁を破られないことではなく、**破られても被害を封じ込めること**（多層防御・爆発半径の局所化）。
