# プログレッシブエンハンスメント

すべてのユーザーに**本質的なコンテンツと機能のベースライン**を届けたうえで、能力の高い環境にだけ体験を上乗せしていく設計思想。2003年3月11日のSXSW Interactiveで Steven Champeon と Nick Finck が「Inclusive Web Design For the Future」という発表で名付けた。

## 3層で積む

| 層 | 担当 | 無くても |
| --- | --- | --- |
| HTML | 本質的なコンテンツと機能（文書構造、リンク、フォーム） | 成立しない |
| CSS | 見た目・レイアウト | 読める |
| JavaScript | 高度なインタラクション | 使える |

各層が下の層を**壊さずに拡張する**のが要点。「JSが無いと何も表示されない」構造は、この積み方をしていない。

## graceful degradation との違い

しばしば対概念として並べられる。

- **graceful degradation（優雅な劣化）** — 高機能な環境を前提に作り、能力の低い環境では**うまく壊れる**ように配慮する。**上から下**
- **progressive enhancement** — 最小限の環境で動くものを作り、能力に応じて**足していく**。**下から上**

出発点が違うだけで両方とも妥当な戦略であり、実務では補い合う。ただし到達点は同じにならない。上から作ると「劣化した状態」は常に事後の配慮になるが、下から作ると最小構成が**最初から動作確認された状態**になる。

## 「JSが動かない環境」は古いブラウザのことではない

2003年当時の動機は「JSを切っているユーザー・古いブラウザ」だったが、現代でJSが動かない主要因はそこではない。

- バンドルのCDNへのリクエストが失敗する／タイムアウトする
- 電車・地下・海外ローミングなどでダウンロード途中に接続が切れる
- 1つのJSエラーやパースエラーで、そのバンドル全体が起動しない
- ブラウザ拡張・企業プロキシ・コンテンツブロッカーがスクリプトを止める
- 検索エンジン・SNSのクローラなど、JSを実行しない／遅れて実行するクライアント

つまり**JSは「来ないかもしれない」のではなく「来るまでに時間がかかる／たまに来ない」もの**。これは[[hydration|ハイドレーション]]が終わるまでの「見えているのに押せない」区間の話とも地続きで、程度の差でしかない。

## 実践の型

**土台をブラウザのネイティブ機能で作り、JSはその上書き**にする。

```html
<!-- JSが無くても送信できる。JSがあれば preventDefault して非同期送信に差し替える -->
<form method="post" action="/notes">
  <input name="title" required>
  <button>保存</button>
</form>
```

- リンクは`<a href>`にする（`<div onClick>`で遷移を実装しない）。新しいタブで開く・URLをコピーする・クローラが辿る、が全部無料で付いてくる
- フォームは`method`と`action`を持つ`<form>`で書き、`required`や`type="email"`などネイティブのバリデーションを土台にする
- 機能検出（feature detection）で分岐する。UA文字列での判定ではなく「その機能があるか」を見る
- CSSも同様に`@supports`で上乗せする

Remix系のフレームワークやNext.jsのServer Actionsが`<form>`を土台に置いているのは、この思想の実装。JSが読み込まれる前に送信されても成立する。

## 「段階的に上げられる」という設計判断

[[astro|Astro]]の構成が分かりやすい例で、必要な量に応じて段階を選べる。

1. 何も足さない（静的HTMLのみ、JS 0KB）
2. 素の`<script>`を1つ足す（テーマ切替のような小さな上乗せ）
3. [[islands-architecture|アイランド]]としてUIフレームワークを1コンポーネントだけ持ち込む
4. ページ全体をクライアントアプリにする

段階1〜2で済む要件に段階4を選ぶ、というのがSPA全盛期に起きたことだった。プログレッシブエンハンスメントは「JSを使うな」という主張ではなく、**必要な段階まで上げてそこで止める**ための物差しとして働く。

## 限界

すべての機能がJSなしのベースラインを持てるわけではない。地図の操作、リッチテキストエディタ、リアルタイム描画、WebRTCなどは「JS無しでも使える簡易版」を作るコストが機能そのものより高くなりうる。この場合の現実的な落とし所は、**JSが要る機能とそうでない機能を分け、コンテンツと主要導線だけベースラインを保証する**こと。「記事は読める・リンクは辿れる・フォームは送れる」までを守り、その上の作り込みはJS前提にする。

全部か無かで判断すると「どうせ全機能は無理だから」と土台ごと捨てることになりやすい。
