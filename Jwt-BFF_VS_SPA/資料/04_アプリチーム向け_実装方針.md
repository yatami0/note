# 【チーム内】認証認可 実装方針とチェックリスト

宛先：アプリケーションチーム（我々）
目的：確定した設計方針を実装レベルに落とす。根拠は [調査まとめ.md](../調査まとめ.md)〜[調査まとめ5.md](../調査まとめ5.md)。

---

## 1. 確定方針（変更する場合はチーム議論を経ること)

1. **Web UIはBFFパターン（IETF §6.1）**：トークンはブラウザに一切出さない。ブラウザが持つのはHttpOnlyセッションCookieのみ
2. **セッションは第一案Redis（1a）、代替案=暗号化Cookie＋IdPリフレッシュ（1b′）の2案並行**：分岐条件は「失効遅延の許容値」（0秒必須→1a、AT寿命≦5〜15分の遅延許容→1b′可）。監査要件の回答で確定するまで、**セッション層はインターフェースで抽象化し両対応で実装**する（[資料00 §3](00_全体像_現状と展望.md)） 。純粋な1b（失効チェックなし）は採用しない
3. **APIはOAuthリソースサーバ**：共通IdP発行のJWTのみ受理。呼び出し元（自前BFF/ベンダーアプリ）で処理を分岐しない
4. **人間の操作＝ユーザーのトークン、バッチ＝client_credentials**。方式(a)/(b)の確定を待たずにこの前提で実装する

## 2. セッション／Cookie実装（BFF側）

- [ ] Cookie属性：`HttpOnly` / `Secure` / `SameSite=Lax`（可能なら`Strict`）/ `Path=/` / `Domain`属性は**付けない**
- [ ] セッションIDは暗号論的乱数（128bit以上）。ログイン時に**セッションID再生成**（session fixation対策）
- [ ] Redisのセッション値にアクセストークン・リフレッシュトークンを保持。**トークンをCookie・localStorage・クライアントstateに置かない**
- [ ] TTL：アイドルタイムアウト（例：30分、操作で延長）＋絶対タイムアウト（例：12時間）。会計操作画面はより短く設定できる設計に
- [ ] ログアウト＝Redisセッション削除（Cookie削除だけで済ませない）
- [ ] 管理機能として「特定ユーザーの全セッション削除」「全セッション削除」を最初から作る（インシデント対応・退職処理用）

## 3. Next.js 実装規律（トークン非露出の5ルール）

- [ ] **R1**：トークンは常に `cookies()` → Redis経由で取得。モジュールスコープ・環境変数・propsで引き回さない
- [ ] **R2**：Server Actionは別ファイル（`actions.ts`）トップレベルに定義。**クロージャに秘匿値を掴まない**（掴むと暗号化されてクライアントに送信される）
- [ ] **R3**：Client Componentへはドメインオブジェクトを渡さず、**表示用DTOに剥がして渡す**（データアクセス層でDTO変換を強制）
- [ ] **R4**：`next.config.js` で `experimental.taint` を有効化し、トークン・セッションオブジェクトに `experimental_taintUniqueValue` / `taintObjectReference` を付ける
- [ ] **R5**：サーバ専用モジュールに `import 'server-only'` を必ず入れる
- [ ] CSRF：Server ActionsはOrigin検証が組み込み。**Route Handlerの変更系（POST/PUT/DELETE）にはOriginチェックを自前実装**
- [ ] `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` をSecrets Managerから注入（マルチインスタンスで必須）
- [ ] CSP導入：nonceベース `script-src`、`connect-src` も絞る

## 4. API（リソースサーバ）実装チェックリスト

- [ ] JWT検証：署名（JWKS、キャッシュ＋kidローテーション追従）／ `iss` ／ `aud` ／ `exp`（clock skew許容±60秒程度）
- [ ] `scope` 検証：エンドポイント×HTTPメソッド単位で必要スコープを宣言的に定義（`master:read/write`, `accounting:read/write`）
- [ ] **`alg` を許可リストで固定**（`RS256`等。`none`・HS系への切替攻撃を拒否）
- [ ] トークンをログに出さない（マスキング）。`Authorization` ヘッダをアクセスログから除外
- [ ] 認可の粒度：scopeは「アプリに許す範囲」、ユーザー単位のデータ認可（この`sub`はこのデータを見てよいか）は**アプリケーション層で別途実装**（scopeだけで済ませない）
- [ ] client_credentialsトークン（`sub`=アプリ）で人間操作系エンドポイントを呼ばれた場合の扱いを決めておく（方式(b)確定後は拒否）

## 5. 監査ログ仕様（ドラフト）

全ての参照・更新APIで以下を構造化ログとして記録：

| フィールド | 内容 | 取得元 |
|---|---|---|
| `who` | 操作者 | JWT `sub`（+ `email`等のクレーム） |
| `via` | 経由アプリ | JWT `azp` / `client_id` |
| `when` | 時刻（UTC, ISO8601） | サーバ時刻（NTP同期前提） |
| `what` | 操作内容 | エンドポイント＋メソッド＋対象リソースID |
| `result` | 成功/失敗（4xx/5xx区分） | レスポンス |
| `request_id` | 追跡ID | ミドルウェアで採番、BFF→API間で伝搬 |

- 更新系は変更前後の値（またはdiff）を残すかを業務側と要確認（会計データは残す方向）
- ログの保存期間・改ざん防止はお客様回答（資料01のQ3）待ち。実装は出力先をCloudWatchに抽象化しておく

## 6. テスト観点

- [ ] 失効テスト：Redisセッション削除後の次リクエストが401になること（ブラウザ側Cookieが残っていても）
- [ ] 改ざんJWT・期限切れJWT・`aud`違いJWT・scope不足JWTがそれぞれ401/403になること
- [ ] Server Actionのクロージャにトークンを掴むコードがビルドに混入していないか（taint APIが例外を投げることの確認テスト）
- [ ] RSCペイロード検査：主要画面のペイロードに秘匿フィールドが含まれないことの自動チェック（E2Eでレスポンスbodyをgrep）
- [ ] CSRF：クロスオリジンからの変更系リクエストが拒否されること
- [ ] セッション固定：ログイン前後でセッションIDが変わること

## 7. やらないこと（アンチパターン集）

- ❌ トークンをlocalStorage / sessionStorage / JS可読Cookieに置く
- ❌ 「同一クラスタ内だから」を理由に認証・TLSを省略する
- ❌ ベンダーから `X-User-Id` ヘッダで利用者を受け取って信用する（自己申告は認証ではない）
- ❌ JWTの中身をデコードして信用する前に署名検証を省く
- ❌ 独自の暗号・独自のセッション機構を自作する（実績あるライブラリを使う）
