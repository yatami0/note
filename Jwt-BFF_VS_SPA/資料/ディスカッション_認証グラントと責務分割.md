## 1. 「共通IdP発行のJWTのみ受け付けるOAuthリソースサーバ」とは（用語の土台）

### 登場人物

- **IdP（認可サーバ）** … トークンを**発行する**役。ここでは Cognito。
- **リソースサーバ** … 守るべきAPI。トークンを**検証して**通す/弾く役。ここでは我々のマスタAPI・会計API。
- **クライアント** … トークンを持ってAPIを叩きに来る側。BFF や ベンダーアプリ。
- **JWT** … 「発行者の署名付きJSON」。`{ sub:誰, iss:発行者, aud:宛先, exp:期限, scope:許可範囲 }` を含み、IdPの秘密鍵で署名されている。

### 「リソースサーバとして作る」＝ 入口に検証ミドルウェアを1枚置き、全リクエストで同じ検証を通す

| 検証 | 意味 | 失敗時 |
|---|---|---|
| 署名（JWKS） | 本当にCognitoが発行したか | 401 |
| iss | 発行者が信頼する1つのCognitoか | 401 |
| aud | 宛先が我々のAPIか（使い回し防止） | 401 |
| exp | 期限切れでないか | 401 |
| scope | そのエンドポイントを叩く権限があるか | 403 |
| alg固定 | 署名アルゴリズムを固定（`none`攻撃拒否） | 401 |

### なぜ発行元（iss）を1つに絞るのか

- **① 呼び出し元で分岐しなくてよい**：BFFでもベンダーでも検証は同一。「相手が誰か」でなく「正しいチケットを持つか」だけを見る → 方式論争と切り離して実装着手できる。
- **② 信頼の起点が1点に集約**：守る対象が「Cognitoの署名を信じる」の一点になる。入口は狭いほど守りやすい。
- **③ 将来の統一IdP移行が設定差し替えで済む**：`iss` を設定値化しておけば、全社IdPが建ってもコードを触らず移行できる。

> **要点**：APIは「相手が誰か」を見ずに「正しいチケットを持つか」だけを見る。そのチケットを発行してよいのはCognitoただ1つ。

## 2. 「サービス間連携は client_credentials グラント」とは

### グラント ＝ トークンをもらう手続きの種類

| グラント | 使う場面 | トークンの `sub`（主体） |
|---|---|---|
| Authorization Code + OIDC | **人間**がブラウザでログイン | ユーザー個人 |
| **client_credentials** | **人間が介在しない**プログラム同士 | アプリ/サービス自身 |

client_credentials は「client_id + client_secret（＝プログラム用のIDとパスワード）」をIdPに提示して直接トークンをもらう方式。ログイン画面は出ない。

```
バッチ処理 --(client_id + secret)--> Cognito
バッチ処理 <--(JWT: sub=batch-app, scope=accounting:read)-- Cognito
バッチ処理 --(Bearer JWT)--> 我々のAPI
```

### なぜバッチはこれを使うのか

- 夜間バッチ・定期連携には「操作する人間」がいない → ログイン画面を出せない → ユーザー用グラントは成立しない。
- `sub` がアプリ名義になり、監査ログに「これはバッチがやった操作」と正しく残る。
- スコープを最小に絞れる。

### 人間の操作 vs バッチを混ぜない

- 人間の操作 → ユーザーのトークン
- バッチ → client_credentials（sub=アプリ）
- **client_credentialsトークンで人間操作系エンドポイントを叩かれたら拒否**（方式b確定後）。これで「バッチが人間のフリをする」抜け道を塞ぐ。

## 3. 方式A（client_credentials） vs 方式B（OIDC）の本質的な違い

### Q. 当初想定はclient_credentials、変更提案はOIDC。この2つの違いがわからない。

**決定的な違いは「ユーザーがどこでログインするか」。**

#### 方式A（当初想定）

```
ベンダーの利用者 ──ログイン──> ベンダー独自の認証（我々のIdPは無関係）
                        ベンダーアプリ（1個のプログラム）
              我々のCognitoから client_credentials でトークン取得
                        sub = vendor-app
                              ▼  我々のAPI
```

利用者は我々のCognitoにログインしない。我々のAPIから見えるのは「ベンダーアプリ」という1個のプログラムだけ。誰が操作しても届くトークンは全部 `sub=vendor-app`。

#### 方式B（変更提案）

```
ベンダーの利用者 ──ログイン──> 我々のCognito（OIDC）
                        ベンダーアプリ（OIDCクライアント）
                        sub = 田中さん個人, azp = vendor-app
                              ▼  我々のAPI
```

利用者が我々のCognitoにログインする。ベンダーアプリは「ログインは我々のCognitoに任せる」OIDCクライアントになる。届くトークンは `sub=田中さん個人`。

### 一段深く：方式Aは「マシン用グラントを人間操作の入口に使っている」

| | client_credentials（方式A） | OIDC（方式B） |
|---|---|---|
| トークンの主体 | アプリ自身 | ログインした人間 |
| ログイン画面 | 出ない | 出る |
| `sub` | vendor-app | ユーザー個人 |
| 本来の用途 | マシン間通信（M2M） | 人間のログイン |

ベンダーアプリの裏には人間がいるのに、我々に見せる顔は「1台のマシン」。だから「誰が」の情報が我々側から落ちる。これが §4-A の既知ギャップ（すべて vendor-app 名義で記録され、どの個人かは我々側の記録に存在しない）。

## 4. 「client_credentialsで外部にAPIを叩かせる」は一般的か？成立するか？

### Q. 外部からIdPでトークン取得してAPIを叩く、これは一般的？成立する話？

**結論：完全に標準。B2B API連携の教科書的な形。**

正式名は **M2M（Machine-to-Machine）認証** / **サービスアカウント方式**。実例：

- AWS … IAMのアクセスキー/シークレットでAPIを叩く
- Google Cloud … サービスアカウントのキーでAPIを叩く
- Auth0 / Okta … 「M2M Application」として正面から提供
- Stripe / SendGrid … APIキーを発行してAPIを叩く

### 「外部」の意味を正確に

「外部＝どこの誰とも知れない相手」ではない。ベンダーは組織的には他社だが、IdP（我々のCognito）から見れば**事前に登録し、client_id と secret を払い出した既知のクライアント**。

```
① 我々がCognitoにベンダー用クライアントを登録 → client_id + secret を安全に渡す
② ベンダーは secret でCognitoからトークン取得（secretを知らない第三者は取れない）
③ トークンをBearerで付けて我々のAPIへ
④ 我々のAPIは 署名/iss/aud/exp/scope を検証して通す
```

secret は「プログラム用パスワード」。無条件開放ではない。

### 方式Aは「正しくない」のか → No。ただし限界がある

- ✅ 成立する・安全（secretで守られ、scopeで最小権限、署名検証も効く）
- ⚠️ ただし「ベンダーアプリ経由の操作が社内/外部の誰の操作か」が我々のログに残らない

→ 会計データでJ-SOX等の個人証跡が要るなら方式Bに格上げ。これが **論点①**。
**「aが間違いでbが正解」ではなく、「個人単位の操作証跡が要件か？」の答えでどちらを採るかが決まる分岐。**

## 5. 方式Bに格上げした場合の責務分割

### Q. 我々のCognitoが全ユーザーの認証を持つ？責務がデカくなりすぎでは？

**「認証を持つ」を1つの塊で考えると重すぎて見える。4層に分解すると、新規に抱える部分は限定的。**

| 層 | 中身 | 誰が持つ（方式B） |
|---|---|---|
| ① 本人確認（パスワード保管・MFA・本人判定） | 認証の実務 | **社内=既存ID基盤（据え置き）／外部=Cognito or ベンダー** |
| ② トークン発行・フェデレーションのハブ | 認証結果を束ねてJWT発行 | Cognito（インフラが構築・運用） |
| ③ ガバナンス（トークン仕様・scope定義・クライアント審査） | 信じるルール | **我々**（むしろ主導権として取りに行く） |
| ④ 運用実務（払い出し・棚卸し・ヘルプデスク） | 日々の人手作業 | **持たない**（分担表で明文化） |

### ① 社内ユーザーはCognitoが「持たない」＝フェデレーション

```
社内既存ID基盤 <-.フェデレーション.-> Cognito
```

社内ユーザーがログインすると、本人確認は既存ID基盤が行い、Cognitoはその結果を受けてJWTを発行するだけ。**パスワードはCognitoに保存されない。** 社内ユーザーについて我々が新規に抱える認証実務はゼロ。

### ③④ 「オーナーの重さ」＝ ガバナンスと運用を切り分ける

§5「我々がIdPオーナーを振られる」の行の通り：**ガバナンス（③）は持つ、運用実務（④）は持たない**を分担表で明文化して条件付きで受ける。

| | 我々（ガバナンス） | インフラ/情シス | ベンダー | お客様 |
|---|---|---|---|---|
| トークン仕様・scope定義（③） | ◎ | | | |
| 接続クライアント審査（③） | ◎ | | | |
| Cognito基盤の構築・運用（②） | | ◎ | | |
| 既存ID基盤⇔Cognitoフェデレーション | 協力 | ◎ | | |
| 社内ユーザーの本人確認（①） | | ◎据え置き | | |
| 外部ユーザーの払い出し・棚卸し（④） | | | ◎ or 協力 | ◎承認 |
| パスワードリセット等ヘルプデスク（④） | ✗ | | ◎ | |
| ベンダーアプリのOIDC改修 | | | ◎ | |

> **要点**：「認証を全部背負う」のではなく「信頼のルール(③)とハブ(②)は持つが、パスワード保管(①社内)と日々の運用(④)は他者に残す」。

## 6. 用語と前提の確認：社内ユーザー・外部ユーザー・既存ID基盤

### Q. 「社内ユーザー」はベンダーのコアシステム利用者のこと？

**No。社内/外部の区別は「どのシステムを使うか」ではなく「誰か（所属）」で決まる。**

| | 社内ユーザー | 外部ユーザー |
|---|---|---|
| 正体 | 自社の従業員（既存ID基盤に登録済み） | 社外の人（既存ID基盤に居ない） |
| 我々のサイト（BFF） | 使う | 使わない |
| ベンダーのコアシステム | **使う** | **使う** |
| 本人確認の実体 | 既存ID基盤にフェデレーション | Cognito収容 or ベンダー連携 |

ベンダーのコアシステムは**社内・外部の両方が使う**。だから「ベンダーシステムの利用者」＝社内ユーザー、ではない。社内ユーザーは「既にID基盤に居るから」Cognitoが持たなくて済む。外部ユーザーは既存基盤に居ないので、新規収容が論点になる。

### Q. AD/Entra とは？うちは Google Workspace では？

- **AD = Active Directory / Entra ID = Microsoft Entra ID（旧 Azure AD）**。Microsoft製の「会社の従業員ID台帳＋認証基盤」。
- §4-B の「AD / Entra ID」は**「既存の社内ID基盤」の代表例として置いているだけ**。
- **本件の実体は Google Workspace**。従業員アカウントは Google が持っているので、既存ID基盤 = Google Workspace と読み替える。

```
社内ユーザー（従業員）
   → Cognito「あなたはGoogleの人ですね、Googleでログインしてきて」
   → Google Workspace が本人確認（Googleのパスワード・2段階認証）
   → Google「本物です」→ Cognito がJWT発行（sub=ユーザー）
```

CognitoはGoogleを外部IdPとして標準サポート（SAML/OIDC）。従業員のパスワードはGoogleの中にあり、Cognitoは持たない。

> ⚠️ **§4-B の図の「社内既存ID基盤(AD / Entra ID)」は「Google Workspace」に修正すべき**（事実誤認を残さない）。

### Q. 外部ユーザーを払い出すのはベンダーのコアシステム。方式Bだと我々のCognitoが管理する必要が出る？

**トークン発行の起点として「外部ユーザーが誰か」をCognitoが知っている必要はある（個人証跡のため必然）。ただし「管理」と「日々の払い出し作業」は分けられる。** 収容方式は2通り：

#### 収容方式A：Cognitoに直接収容

```
ベンダーが外部ユーザーを登録 → 実体はCognitoに作られる（管理API/SCIM経由）
外部ユーザーがログイン → Cognitoが直接認証 → sub=外部ユーザーのJWT
```
- Cognitoがパスワードも保持。我々の管理負担は大きめ。

#### 収容方式B：ベンダーIdPをフェデレーション

```
ベンダーが外部ユーザーを登録 → 実体はベンダー側のまま
外部ユーザーがログイン → ベンダーIdPで本人確認
                       → Cognitoが「ベンダー経由のユーザー」として受けてJWT発行
                       → sub=外部ユーザーのJWT
```
- Cognitoはパスワードを持たない（社内をGoogleに委譲するのと同じ構造を、外部はベンダーに委譲）。
- 払い出し・パスワード管理はベンダーに残る。

| | 我々のCognito | ベンダー |
|---|---|---|
| 外部ユーザーを**トークン上で識別**（③） | ◎必要 | |
| アカウントの**日々の払い出し・棚卸し・パスワードリセット**（④） | 持ちたくない | ◎残せる（特に収容方式B） |

→ 「我々が管理する必要が出る」は**半分Yes（識別は担う）・半分No（運用は残せる）**。これがフェーズ2Bの「外部ユーザーの収容設計（我々＋ベンダー＋お客様）」で決める設計項目。

### 一行まとめ

- **方式A/Bの違い** ＝ ユーザーがどこでログインするか（ベンダー内 / 我々のCognito）。監査証跡が要件かで選ぶ。
