# JWT / BFF vs SPA トークン管理 — 次セッションでの検討テーマ

## この文書の目的

Next.js（App Router / Route Handler をBFFとして利用）を前提に、認証情報（トークン）の
置き場所として **「BFF + セッション（Redis）」** と **「SPA + トークンをブラウザ保持」** の
どちらを採るべきかを判断したい。

前提として、ここまでの議論で以下の原則整理は済んでいる：

- 「XSSが絶対にない」は**証明不能な前提**（不在の証明はできない／存在は1例で証明される）。
- 堅牢な設計とは「壁を破られないこと」ではなく「破られても被害を封じ込めること」
  （Secure by Design / 多層防御 / 攻撃対象領域の縮小 / 爆発半径の局所化）。
- bearer token は **capability**（持てば行使できる＝漏れると持ち出して悪用可能）、
  session ID は **reference**（サーバ状態への参照＝サーバが消せば即失効）。
- したがって最終的な問いは「SPAか否か」ではなく、
  **「トークンをブラウザに出す代わりに得るものが、そのXSSリスクとBFFコストに見合うか」**。

**未解決で、次セッションで詰めたい問いが2つある（下記）。**

---

## 中心となる問い

> **トークンをブラウザに出す代わりに得るものが、そのリスクとBFFコストに見合うか？**

これを、抽象的な「メリット」で終わらせず、実在するかを1つずつ潰して判断したい。

## 検討すべき観点（洗い出し）

### 観点A：Next.js の Server Actions / Server Components でも結局トークンは露出するのでは？

ここは重要な疑問。「BFFにすればトークンはフロントに出ない」と言っていたが、本当か。
次の点を切り分けて検証したい。

- **Server Actions は本当にサーバでのみ実行されるのか。**
  Server Action の関数本体・クロージャに掴んだ変数（トークン等）はクライアントJSバンドルに
  含まれるのか、含まれないのか。RSC のシリアライズ境界で「何がクライアントに送られるか」を正確に把握する。
- **Server Component が取得したデータの扱い。**
  Server Component 内でトークンを使ってfetchした場合、トークン自体はHTMLペイロードやRSC
  ペイロードに載って漏れないか。載るのは「取得結果」だけで「トークン」は載らない、という理解で合っているかを確認。
- **`"use client"` 境界を越えて props で渡すと露出する**という落とし穴。
  うっかりトークンをClient Componentのpropsに渡すと、RSCペイロード経由でブラウザに出る。
  これは構成の問題ではなく実装ミスの問題だが、「BFFなら自動で安全」ではないことの根拠になる。
- **cookies() / headers() でセッションIDを読む形なら、トークン本体はサーバに留まる**という
  想定が正しいか。Redis参照 → トークンはサーバメモリ内のみ、というフローを図で確認したい。
- 結論として問いたいのは：
  **「Server Actions/Componentsを正しく使えばトークンはブラウザに出ない」は成立するのか、
  それとも一定の実装規律を守って初めて成立する条件付きの話なのか。**

### 観点B：そもそもXSSはどれほどの脅威なのか？（リスクの実測）

「XSSリスクを引き受ける」と繰り返してきたが、その確率と影響を具体化しないと天秤が組めない。

- **XSSの発生確率をどう見積もるか。**
  自前コードだけでなく、依存ライブラリ・サードパーティスクリプト（広告、解析、タグマネージャ、
  A/Bテストツール、チャットウィジェット）が攻撃面を広げる。自分のサービスは何を読み込んでいるか棚卸しする。
- **CSP（Content Security Policy）でどこまで潰せるか。**
  `script-src` の厳格化・nonce/hash 運用で XSS の実害をどれだけ下げられるか。
  ただし CSP も「完全ではない」前提で、CSPがある場合とない場合で天秤がどう動くか。
- **XSSがあった場合、方式ごとに実際に何が起きるかの比較。**
  - SPA+トークン：トークンを**持ち出して**攻撃者サーバから有効期限まで悪用（持続的・オフライン）。
  - BFF+セッション：Cookieは持ち出せず、被害者ブラウザ・生存セッション内に**封じ込め**、Redisで即失効。
  この差は認めつつ、「XSSがあればBFFでもセッションライディングでAPIは叩ける」という反論の
  実際のインパクト（被害の持続時間・範囲）を定量的に評価する。
- **脅威モデルを明示する。** 誰から何を守るのか。
  - 守る資産の価値（金融/医療/管理者権限 か、影響の小さい社内ツールか）。
  - 攻撃者の想定（無差別bot か、標的型か）。
  - 侵害時の最悪シナリオ（何が起きると事業として致命的か）。
- 結論として問いたいのは：
  **XSSは「確率は低いが影響が壊滅的」なのか「そこそこ起こるが影響は限定的」なのか、
  自分のサービスではどちらの象限にあるのか。**

### 観点C：「得るもの」を3分解して実在チェック

トークンをブラウザに置いて得られるものを分解し、自分のシステムで実在するか各々潰す。

| 得るもの | 本当に価値がある条件 | 自分の状況で実在するか（要記入） |
|---|---|---|
| (1) サーバのステートレス性 | 超大規模、Redis運用が真に重荷、水平スケールが要件 | ← 検討 |
| (2) 実装の単純さ | 素のAPI構成でBFF層追加が重い | ← Next.jsだと逆転する可能性 |
| (3) マルチクライアント | Web以外（モバイル/3rd party）が**実在**する | ← 今Web専用ならYAGNI |

- (1) ステートレス性：JWT自体はBFFでもサーバ保持できる。失うのは「Redisを持つコスト」だけ。
  一方JWTは**即時失効ができない**弱点があり、運用ではこちらが刺さることが多い。本当に要るか。
- (2) 単純さ：安全なトークン方式（メモリ保持＋リフレッシュトークンHttpOnly＋サイレントリフレッシュ
  ＋ローテーション）は結局複雑。「単純」に見えるのはセキュリティを妥協している場合では。
  さらにNext.jsではRoute Handlerが同居しBFF追加コストが低いため、この優位は**逆転**しうる。
- (3) マルチクライアント：「将来モバイルを出すかも」で選ぶのはYAGNI。今Web専用なら価値ゼロ。

### 観点D：BFF側のコスト（天秤の反対側）

BFFを選ぶ場合に手放す／背負うものも正直に列挙して比較する。

- Redis（セッションストア）の導入・可用性・運用。**Redisの可用性 = 認証の可用性**になる点。
- ステートフルになることでのスケール時の考慮（セッション共有、スティッキーではなく共有ストア前提）。
- CSRF対策が必要になる（Cookieベースゆえ）。ただし `SameSite` で大きく軽減。
- 実装・テスト・デバッグの複雑性が、Next.js文脈では**どれだけ相殺されるか**を評価。

### 観点E：判断のための決め手（意思決定基準）

上記を踏まえ、最終判断を分ける決定的な質問リスト：

1. このサービスで扱う資産の価値は？（漏洩の被害の大きさ）
2. 攻撃面はどれくらい広い？（サードパーティスクリプトの数、依存の多さ）
3. 即時失効・集中管理は要件か？（コンプラ、退職者無効化など）
4. 実在するマルチクライアント要件はあるか？（今、将来確定しているか）
5. Redis運用のコストは現実的に重いか？
6. Next.jsのServer機能で、トークン非露出を規律をもって維持できるか？（観点A）

→ 1〜3が「重い/要る」に寄り、4〜5が「軽い/不要」に寄るほど **BFF+セッション**が正当化される。
逆に4が強く実在し1〜3が軽いなら **トークン方式**が正当化される。

## 次セッションへの依頼（fable5 へ渡すプロンプト案）

> 添付の検討メモをもとに、以下を順に深掘りしてほしい。
>
> 1. **観点A**：Next.js（App Router）の Server Actions / Server Components / RSC の
>    シリアライズ境界を技術的に正確に説明し、「トークンはブラウザに出ない」が
>    どういう条件下で成立し、どういう実装ミスで破れるかを具体例で示してほしい。
>    「BFFにすれば自動的にトークンが出ない」という理解が正しいのか、条件付きなのかを結論づけてほしい。
>
> 2. **観点B**：XSSの脅威を「発生確率 × 影響」で定量的に捉える枠組みを提示し、
>    CSPでどこまで軽減できるか、方式ごと（SPAトークン / BFFセッション）に
>    XSS発生時の被害（持続時間・範囲・失効可否）がどう違うかを整理してほしい。
>
> 3. **観点C〜E**：私のケースに当てはめて「得るもの」の実在チェックと天秤を一緒に埋めてほしい。
>    （私のサービスの前提は次セッションで補足する：資産の価値／クライアントの種類／規模／読み込む3rdパーティ等）
>
> 最終的に「私のケースではどちらを採るべきか」を、理由つきで結論してほしい。
> 一般論ではなく、上記の観点を1つずつ潰した上での判断がほしい。
